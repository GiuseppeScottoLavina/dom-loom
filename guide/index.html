DomLoom guide

Getting started

DomLoom draws ordinary HTML controls through one WebGPU compositor, with the motion and light of a game interface. You write a form; DomLoom makes every press, choice and change answer. This guide shows each feature with a live example and the exact code that runs it.

Install

        npm install dom-loom

Import the stylesheet and the library once, in your app's entry module:

        import 'dom-loom/style.css';
        import 'dom-loom';

dom-loom brings every component; you can import fewer. Serve the page from localhost or HTTPS: WebGPU needs a secure context.

Your first stage

Put the controls that belong together inside one <loom-stage>. Everything else is the HTML you already know: DomLoom recognises the standard elements inside a stage.

Tab through the fields and watch the brackets follow focus. Press Deploy briefly: it refuses with a shake. Hold it until it fires. Leave Callsign empty first, and the field glitches.

The guide gives its examples a little layout (a grid with gaps), as your page's CSS would. DomLoom draws the controls; it does not lay out your page.

The form is still a form: it validates, submits, autofills and is read by screen readers as usual. The hold attribute makes the button fire only after a hold; keyboard and screen reader users confirm with a second activation instead.

What a stage does

When it starts, a stage moves its content into a <canvas> that the browser keeps drawing as live HTML (HTML-in-Canvas). A WebGPU compositor draws that picture every frame something moves, and adds the effects: dents, light, cuts, flights. The elements stay where they are, focusable and clickable, and a click lands on what is drawn under the pointer, even while it moves.

  • One stage per panel. A stage is one canvas. Wrap a panel or a form, not each control.
  • Nothing renders at rest. A stage draws frames only while something moves.
  • Without WebGPU, in forced colours or after a GPU failure, the same markup is styled in plain CSS and keeps working.
  • With reduced motion, springs snap, transitions swap at once and nothing shakes.

A stage is an opaque rectangle: put it on a background of its --loom-void colour (#0a0e24 in the default skin), so its cut corners blend in.

Which path is running

stage.ready resolves with 'webgpu' or 'dom', and the stage carries data-renderer (webgpu, loading, dom) and data-mode (native on Chrome's own HTML-in-Canvas, polyfill elsewhere). If the compositor fails, the stage fires loom-fallback and goes back to plain HTML.

Reading stage.ready starts a stage that has loading="lazy", so read it only for the stage you want to start.

Stage attributes

AttributeWhat it does
soundProcedural interface sounds (WebAudio, no files), after the first gesture in the stage.
hapticsShort vibrations on toggles and on a completed hold, where the device has them.
loading="lazy"Keeps the HTML interactive and starts the GPU when the stage comes within 240 CSS pixels of the viewport. Focus or a press starts it at once.
staticNever starts the compositor: plain HTML styling only.
skinThe skin that draws the stage. The default is holo; see Skins and theming.
overlayA transparent stage inside a <dialog> or a popover; see Overlays.

These are boolean attributes: to turn one off, remove it. Try the sound:

Turn your volume up, then flip the switch and press Ping.

Import only what you use

Each component brings its behaviour, its drawing in the default skin and the compositor primitives it needs, and the shader is built from those primitives only. Import the core and the components you use: 

        import 'dom-loom/core';     // <loom-stage>, transitions, buttons and hold, the focus reticle
        import 'dom-loom/forms';    // choices, ranges, text fields, numbers
        import 'dom-loom/tabs';

And the stylesheets of what you use, instead of dom-loom/style.css:

        @import 'dom-loom/base.css';
        @import 'dom-loom/skins/holo/base.css';   /* standard HTML */
        @import 'dom-loom/skins/holo/toast.css';  /* and the attribute components you use */

A component imported later, from a lazy chunk, joins the stages already running. The polyfill is loaded by the first stage that needs it, in its own chunk; on Chrome's own HTML-in-Canvas its core is not downloaded at all.
